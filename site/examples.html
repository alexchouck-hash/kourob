Three Layers, One Routing Principle

Trooth fetches external data inside a provenance envelope. KouroB answers repeated questions by routing them across small nodes instead of calling a frontier model. Modafied grades sources and nodes with open code. This page is that stack actually running — seven nodes on one machine, four questions asked for real, and the signed record of every hop, which your browser checks for itself.

The Stack

Three Layers That Do Not Control Each Other

Both KouroB and Trooth route the same way — resolve against a registry, rank the candidates, record what was rejected and why. They differ in what they route. Trooth routes fetches: which source. KouroB routes computation: which nodes, in what order. Modafied grades both and is operated by neither, because you cannot honestly grade pipes you resell or nodes you run.

KouroB
routes computation

A typed request arrives and the cheapest thing that can answer it does: a compiled rule or a cached result first, a distilled local model next, a frontier model only on a miss. Anything out of scope is referred to the node that holds it, with the route handed back so the caller does not need the introduction twice.

never fetches an upstream directly
Trooth
fetches, inside an envelope

External data arrives as a signed envelope with the bytes hashed and the fetch time stamped, so provenance is inherited rather than reconstructed. In this example the five source nodes hold envelopes for NWS, Open-Meteo, USGS, BLS and FRED. A fetch is a hop like any other hop, which is what keeps every path uniform and traceable.

never runs a model — its routing is a lookup
Modafied
grades, independently

Six dimensions per source — freshness lag, revision behaviour, correction latency, completeness, schema stability, internal consistency — plus accuracy only where a named anchor exists. The nodes here hold Modafied's emblem for each source as an event, verified against its manifest before it was accepted.

never accepts a self-reported number

The six dimensions are chosen so that gaming one degrades another: publishing early to win freshness raises your revision rate; suppressing corrections to win revision rate raises internal inconsistency; padding fields to win completeness raises schema instability. That trap is published on purpose.

Seven Nodes, Two Of Them Holding Nothing

Click a node for its declared scope and what it holds. Or pick a question and watch which nodes it touches. The route is not configured anywhere central: each routing node knows only its own exclusions and the neighbour each one refers to, and the path is whatever those local decisions add up to.

Green dot = the node holds events and can answer. Amber dot = it holds nothing and only routes. A routing node is still a full node: it meters, records and signs its referral exactly like an answer, because the response envelope {data, rendered, citations, receipt_id} has no exceptions — not for errors, not for referrals.

Routing

Four Levels, Each A Cache In Front Of The Next

The design goal is that cost per query falls as traffic rises. That only happens if the expensive thinking is done once per class of question and replayed afterwards. Here is the ladder, and honestly which rungs this example exercises today.

LevelTriggered whenMechanismIn this example
0 · exact memo The identical typed input has been seen before Hash the canonical input, return the cached typed output. Free. running
1 · class memo A question of a shape already seen Key on a class signature and replay the path that worked, paying only for node inference. partly — every request logs its shape and the route table replays learned routes, but paths are not yet memoized as first-class objects
2 · planner An unknown class, or a referral that patched a path A frontier model plans a path under a hop budget and a hard cost ceiling and returns what it rejected. Async: a miss is an honest 202 queued, never a silent expensive fallback. planned — today a miss cascades to a frontier tier inside one node rather than to a budgeted planner across nodes
3 · distilled planner Enough graded plans exist A small classifier proposes the path; the frontier model verifies a sample. planned — needs a corpus that does not exist yet

Ranking a hop, lexicographically

Among the nodes registered for a task, candidates are eliminated in a fixed order rather than scored by a weighted formula. The reason is not elegance: with a lexicographic order every rejection has a one-line reason, and that reason can be recorded and read back afterwards. A weighted product gives you a number nobody can argue with specifically.

  1. Drop any node without a current grade.
  2. Drop any node below the accuracy floor for the class, on its named anchor.
  3. Drop any node whose p95 latency breaks the caller's budget.
  4. Of what is left, take the lowest declared cost.
  5. On a tie, the most recently regraded.

What this run recorded

Every hop in the next section carries the decision that produced it — the exclusion that matched, the rule that bound, the neighbour that was bridged to — with what the cascade tried first. These are read out of the network's own request log, not written for the page.

Evidence

Real Answers, Real Cost, Verified In Your Browser

Everything below came out of an actual run of the seven nodes: real questions, real answers, real ed25519 signatures, real per-hop cost and latency. You do not have to take that on faith. Your browser recovers each node's public key from its did:key, checks every signature, and walks every hash chain, with no server involved.

Check the ledgers

Seven chains, every record signed by the node that wrote it and hashed into the one before it. Verification runs on your machine, over network.json as served.

What this does and does not prove. It proves these records were signed by the keys behind those did:keys and that nobody has edited the history since: change one byte and the check fails, which is what the tamper button does. It does not prove a node was honest when it signed — a compromised node can sign false records going forward. That needs a transparency log, and saying so is better than implying tamper-proofing that isn't there.

Runbook

Build It Yourself

Seven nodes from one command, in under a second, from public data. Each is kourob init plus its contracts, its rules, and the envelopes it holds — no bespoke wiring.

uv run python examples/trooth-network/build.py

Initialises the five source nodes, puts each feed's envelope, its Modafied emblem and its Trooth scorecard through the ingest gate, then creates the two routing nodes and connects them. Prints each node's did:key and event count, and writes credits.md from what the nodes actually hold.

uv run kourob query 'largest earthquake in the last hour' --node examples/trooth-network/cells/trooth-desk

One hop instead of two: the front routing node sends seismic questions straight to the node that holds them. Swap the question for a CPI one and it lands on bls-node.

uv run python examples/trooth-network/export_web.py --out site/network.json

Regenerates everything in the section above: the questions are asked again for real, and the ledgers, signatures, per-hop cost and cited events are written out exactly as the run produced them. The page has no other source of truth.

Honest fixtures. The envelopes are snapshots of the real public sources — fetched, hashed and time-stamped the way a snapshot job does it — but signed by a local key with key_id: kourob-local. That id is the marker: they prove what was fetched and when, by this operator, not by Trooth. They validate against the same schemas, and nothing downstream changes the day real ones arrive.

What This Example Shows, And What It Doesn't

The plan this is built against gates each phase on a technical, a commercial and a desirability test, and forbids building from a phase whose gate is unmet. So here is the example measured against it, including the parts that are not built.

CapabilityStateWhere you can see it
Provenance envelopes from public sources running Five source nodes; every answer cites the event the envelope became
A node answering from compiled rules, at no model cost running Every answered hop above, at tier T0
Referral, bridging, and a route handed back running The "asked again" thread: three hops become two, and the price falls
Signed, hash-chained records across separately keyed nodes running The verification panel, in your browser
Independent grades held as evidence, verified before acceptance running Each source node holds its Modafied emblem and its Trooth scorecard
A distilled local model taking traffic off the frontier built, not exercised here This network answers from rules alone, so no student is needed yet
Budgeted planner, queued misses, a published rejection list planned —
Path collapse and codification planned Needs a path that has served real traffic without changing
Independent grading replicas agreeing on a hash planned —

The single number that decides whether any of this was worth building is the repetition rate of the first real workload: how often the same class of question comes back. Below roughly a fifth, caching is the wrong bet and the honest move is to keep the pipe and the grader and stop there. This example cannot answer that question. Only traffic can.
